LLM call inventory — every call site, in depth

Eight families. For each: who triggers it, the exact API, the model, what is sent, what comes back, and what (if anything) is recorded today. automatic means no human decides to spend; PII means missing-person personal data leaves the platform in the prompt.

1Case AI Analysisניתוח אירועuser-triggeredcreditsPII
Trigger & caller
User requests analysis on a case → AIJob record → AI Job Worker workflow → runWorker; a parallel path calls queueAnalysis directly. Three near-duplicate implementations exist: queueAnalysis, runWorker, ai/runWorker.
API

Model

Per-chunk JSON summary; final JSON — summary_markdown, recommendations_markdown, risks_markdown, next_questions_markdown, sources.
Calls per run
Up to 8 (7 chunks + 1 final), plus fallback retries → up to ~10 billable calls per button press.
Logged today

Part 3

What's broken about cost visibility today

Every cost field is a hard-coded zero

input_token_estimate: 0, output_token_estimate: 0, cost_estimate_usd: 0 appears verbatim in all three analysis workers. The schema promised tracking; the code never delivered it.

Exact token counts are received and thrown away

Every direct OpenAI response carries a usage object with precise input/output tokens. Not one call site reads it. Half the ledger is free — it's already in the responses.

Five of eight families have no record at all

Transcription, voice notes, translations, simulator, and the agent leave no cost/usage trace. Only case analysis writes anything (zeros) to AIAnalysis.

No timing anywhere

No call records when it started, finished, or how long the provider took — you asked for "time received"; today it exists only in ephemeral console logs.

Unattended spend paths

Inbound voice notes and every interview save spend money with no cap, no alert, no owner. Cost is drivable from outside the organization.

Triplicated analysis workers

queueAnalysis, runWorker, ai/runWorker maintain near-identical prompt/call logic. Instrumenting means touching all three — and is an argument to converge them.

⚠ Base44 credit opacity: InvokeLLM, the agent, emails and OCR bill in credits, and it is not yet verified whether InvokeLLM returns token usage to the caller. Step 1 of the build is a probe: log a raw InvokeLLM response and check. If usage isn't exposed, those calls get estimated tokens (chars÷4) and a credits-based price, with the platform's usage dashboard as ground truth.
Part 4

The capability: a per-call LLM ledger

One shared metering module wraps every LLM call. It never blocks or fails the real call — it times it, captures payloads and usage, prices it, and writes one LLMCallLog row. An admin page reads the ledger.

Call siteany of the ~15 sites, unchanged business logic
→
llmMeter.tsstarts clock · forwards call · reads usage or estimates · prices it
→
ProviderBase44 InvokeLLM · OpenAI · Soniox
→
LLMCallLogone row per call, fire-and-forget write
→
Admin ledger UIdrill-in, rollups, alerts, XLSX

New entity — base44/entities/LLMCallLog.jsonc

{
  "name": "LLMCallLog",
  "properties": {
    "called_at_utc":     { "type": "string", "format": "datetime-local" },   // request sent
    "completed_at_utc":  { "type": "string", "format": "datetime-local" },   // response received
    "duration_ms":       { "type": "number" },
    "status":            { "enum": ["success", "error", "fallback"] },
    "error_message":     { "type": "string" },

    "call_family":       { "enum": ["ניתוח אירוע","סיכום תשאול","תמלול","הקלטת וואטסאפ",
                                    "תרגום","סימולטור","קליטת מלאי","אחר"] },
    "function_name":     { "type": "string" },                // e.g. "processInterviewSummary"
    "triggered_by":      { "type": "string" },                // user email | "workflow" | "inbound-whatsapp"
    "case_id":           { "type": "string" },                // optional, business key

    "api":               { "enum": ["base44_invoke_llm","openai_chat","openai_audio",
                                    "soniox_stt","base44_extract_file"] },
    "provider":          { "type": "string" },                // openai | soniox | base44-routed
    "model_requested":   { "type": "string" },
    "model_used":        { "type": "string" },                // after fallbacks

    "request_payload":   { "type": "string" },                // full prompt / audio URL (see PII note)
    "response_payload":  { "type": "string" },                // full response text/JSON
    "request_chars":     { "type": "number" },
    "response_chars":    { "type": "number" },
    "audio_seconds":     { "type": "number" },                // STT calls

    "input_tokens":      { "type": "number" },
    "output_tokens":     { "type": "number" },
    "tokens_source":     { "enum": ["api_usage","estimated"] },
    "cost_usd":          { "type": "number" },
    "cost_source":       { "enum": ["usage_pricing","estimated","credits_opaque"] },

    "client_request_id": { "type": "string", "unique": true }
  },
  "required": ["called_at_utc","call_family","function_name","api","client_request_id"]
}
🔐 PII decision, made deliberately: storing full request/response follows the existing precedent (AIAnalysis.final_prompt already stores complete case prompts). Entity permissions restrict LLMCallLog to admins, and a retention job purges payload fields (keeping the numeric row) after a configurable window — proposed 90 days.

Shared wrapper — base44/shared/llmMeter.ts

// One module, four wrappers, zero behavior change on the happy path.
export async function meteredInvokeLLM(base44, params, meta)   // wraps Core.InvokeLLM
export async function meteredOpenAIChat(payload, meta)         // wraps /v1/chat/completions — reads usage
export async function meteredOpenAIAudio(form, meta)           // wraps /v1/audio/transcriptions
export async function meteredSonioxStt(base44, args, meta)     // wraps runSonioxTranscription

// meta = { call_family, function_name, triggered_by, case_id }
// Contract: start clock → forward the call untouched → on settle:
//   tokens  = response.usage ?? Math.ceil(chars / 4)        (tokens_source records which)
//   cost    = pricing[model] applied to tokens/audio_seconds
//   write LLMCallLog via asServiceRole — inside its own try/catch:
//   a metering failure must NEVER fail or slow the real call.

Pricing — data, not code

Prices live in a SystemSetting key llm_pricing_json, editable from the admin page: per-model USD per 1M input/output tokens, per-hour STT rates, and a credits-per-call figure for Base44-billed integrations. Shipped empty with the model names found in this audit (gpt-4o, gpt-4o-mini, gpt_5_mini, gpt_5_5, whisper-1, gpt-4o-mini-transcribe, stt-async-preview, plus the Claude/Gemini options in AISettings) — values filled from the providers' current price lists at implementation time, never hard-coded in functions. Unknown model ⇒ cost logged as null, row flagged, never a made-up number.

Part 6

Rollout — safe order, small PRs

  1. Probe InvokeLLM. One temporary log of a raw response to learn whether Base44 exposes token usage. Determines tokens_source for half the ledger. (5-minute experiment, drives the design.)
  2. Ship the ledger core: LLMCallLog entity + llmMeter.ts + llm_pricing_json setting. No call sites touched yet — zero production risk.
  3. Instrument the direct-OpenAI sites first (translations, simulator, transcription) — exact usage tokens, immediate accurate dollars.
  4. Instrument the InvokeLLM sites (case analysis, interview summaries) and backfill AIAnalysis.cost_estimate_usd from real numbers instead of 0.
  5. Ship LLMUsage.jsx — ledger, drill-in, rollups, pricing editor, XLSX.
  6. Guardrails: daily-budget alert, voice-note duration cap, retention purge job.
  7. Cleanup (separate PR): converge the three duplicate analysis workers; route inventory OCR through a backend function.
